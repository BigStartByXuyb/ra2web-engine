## 数据格式：MIX 加密头布局（已用真实档案核实）

在真实 `RA2.MIX` 上验证通过的布局（`packages/formats/src/mix.ts` 实现，见 `mix-encrypted.test.ts`）：

| 偏移  | 内容                                                   |
| ----- | ------------------------------------------------------ |
| 0..3  | flags（`uint32`，含 `0x00020000` 表示加密）            |
| 4..83 | Blowfish 密钥材料（80 字节）                           |
| 84..  | 加密索引；其**前 8 字节同时充当"条目数 + 数据区长度"** |

要点：密钥材料的起点是 **4 而不是 0** —— 解析器在进入加密路径前已经读掉了 4 字节 flags。
条目表按 8 字节块解密，数据区起点 = 84 + 表长 + 对齐填充。

这一条曾让实现反复解出错误的条目数（25522 / 25863 而非 21）；错位 4 字节的表现是"解密成功但内容是垃圾"。

## 数据格式：地图 `[IsoMapPack5]`（已用真实档案核实）

在真实 `Maps01.mix` 上核实的布局（`packages/formats/src/map.ts` + `lzo1x.ts`，见 `map.test.ts`）：

| 层   | 布局                                                                                         |
| ---- | -------------------------------------------------------------------------------------------- |
| 文本 | 地图是 INI（windows-1252），`[Map] Size=` 给 left,top,right,bottom                           |
| 编码 | `[IsoMapPack5]` 是数值键的 base64 文本，按键的**数值升序**拼接                               |
| 容器 | 解码后是若干块：`u16 压缩长度` + `u16 原始长度` + LZO1X 压缩数据（单块原始数据 ≤ 8192 字节） |
| 记录 | 每 11 字节：`u16 rx`、`u16 ry`、`i16 tile`、`i16 保留`、`u8 subTile`、`u8 z`、`u8 保留`      |
| 坐标 | `cellX = rx − ry + width − 1`，`cellY = ⌊(rx + ry − width − 1) / 2⌋`                         |

判定依据全部来自数据本身：

- 首张地图（70×96、SNOW）解压前数据里 `11 00 00`（LZO 结束标记）恰好出现 **18 次**，
  而 `⌈11 × (2×70−1) × 96 / 8192⌉ = 18`；块头解出的"压缩长度 / 原始长度"与实际解码长度逐块一致。
- 18 块原始数据合计 146 788 字节 = `11 × (2×70−1) × 96 + 4`（多出的 4 字节是原版余量）。
- 记录数 = `(2×宽−1)×高` = 13 344，其中**正好 6 720 条（= 70×96）落在方格范围内且互不重复**，
  其余是同格的另一半菱形位置 —— 这条恒等式同时验证了坐标换算。
- 该地图实测：tile 索引 178 种（最多 713 / 734 / 0 / 326），z 只有 4 种取值（2 最多，其次 6）。

未核对：`z` 的原版单位（做高度渲染时需要）。

## 数据格式：分块包容器与覆盖物层（已用真实档案核实）

地图里的"包"段共用同一个容器：`[u16 压缩长度][u16 原始长度][压缩数据]` 依次排列，
任一块的长度字段为 0 即结束。**编码器按段位不同**：

| 段                                                      | 编码器          |
| ------------------------------------------------------- | --------------- |
| `[IsoMapPack5]`                                         | LZO1X           |
| `[OverlayPack]` / `[OverlayDataPack]` / `[PreviewPack]` | Format80（LCW） |

两种编码器对"块"的理解不同，这是实测出来的：

- **LZO1X**：每块是独立流，各自解出自己声明的原始长度（块尾 `11 00 00` 结束标记）。
- **Format80**：块只是传输分段，**整条流连续**，回抄下标是**全局输出下标**，会跨块引用。
  实测 `[OverlayPack]` 32 块共解出 262144 字节（= 256 KiB，正是客户端缓冲区的长度）；
  第 2 块开头的 `f4 00 00` 回抄的是全局下标 0。每段以 `0x80` 收尾，因此要按段推进。

Format80 命令表（多字节字段小端）：

| 命令         | 含义                                                                                 |
| ------------ | ------------------------------------------------------------------------------------ |
| `0x00..0x7F` | 从已产出区域回抄，份数 = `(命令 >> 4) + 3`，距离 = `((命令 & 0x0F) << 8) + 下一字节` |
| `0x80..0xBF` | 字面量，份数 = `命令 & 0x3F`；`0x80`（份数 0）表示本段结束                           |
| `0xC0..0xFD` | 从全局下标回抄，份数 = `(命令 & 0x3F) + 3`，下标 = 下一 `u16`                        |
| `0xFE`       | 填充，份数 = 下一 `u16`，字节 = 下一字节                                             |
| `0xFF`       | 从全局下标回抄，份数 = 下一 `u16`，下标 = 再下一 `u16`                               |

三条判定依据：首段 `22 字节 → 8192 字节` 的第一条填充命令按小端解出"7224 个 0xFF"（大端会超出段长）；
份数取**高**半字节（按相反取法该段会多 1 字节）；回抄下标是全局下标（见上）。
回抄允许与已产出区域重叠（距离 1 即"重复上一字节"）。

**覆盖物**：`[OverlayPack]` 给编号、`[OverlayDataPack]` 给附加字节，两份都按
`下标 = 菱形横坐标 + 512 × 菱形纵坐标` 索引，与地形记录一一对应；`255` 表示该格没有覆盖物。

覆盖物画什么，由三样东西合起来决定：

1. 编号查 rules.ini 的 `[OverlayTypes]`（从 1 起，243 个编号）得到图形名；
2. 图形名查 art.ini 得到两条命名规则（`Image=` 缺省时用节名）；
3. 帧号取附加字节，越界或该帧为空时退回第一个非空帧。

实测（`MULTI.MIX` 第 7 张、`Maps01.mix` 第 0 张）：编号 102 = `LOBRDG26`（低桥板，6 帧里只有第 1 帧有图形）、
171..175 = `SROCK01..05`、177 = `TROCK02`、27 = `NAWALL`；编号 24/25/241（`DUMMY15`/`BRIDGE1`/`BRIDGEB1`）
在 art.ini 里没有条目，客户端同样跳过。

**覆盖物与地块共用剧场 iso 调色板**。判定依据：`SROCK01` / `TROCK02` / `LOBRDG26` 用 `isotem.pal`
分别画出石头、枯树、木桥，换成 `temperat.pal`（客户端 theater 设置里的 `overlayPaletteName`）则是杂色。

## 数据格式：SHP 图形（已用真实档案核实）

头部 8 字节：`u16 0`（签名）+ `u16 width` + `u16 height` + `u16 frameCount`。

每帧头 24 字节：`i16 x`、`i16 y`、`i16 width`、`i16 height`、`u8 compressionType`、3 字节保留、
2 个 `i32` 保留、`i32 dataOffset`（帧数据相对文件起点）。帧数据范围 = 本帧 `dataOffset` 到下一帧
`dataOffset`（最后一帧到文件尾）。

| compressionType | 含义                                                                      |
| --------------- | ------------------------------------------------------------------------- |
| `0` / `1`       | 原样 `width × height` 字节                                                |
| `2`             | 逐行前缀 `u16 行长度`，其后是该行的字节                                   |
| `3`             | 逐行前缀 `u16 行长度`，行内**每个非零字节就是一个像素**，`0` 是零游程转义 |

要点：

- **宽或高为 0 的帧是合法的空帧**（实测 `LOBRDG26.tem` 6 帧里有 3 帧如此，`dataOffset` 也是 0），按"没有图形"处理。
- 透明索引是 `0`；帧自带的 `x` / `y` 是它在整幅画布里的位置（`SROCK01` 是 120×120 画布，本体 28×27 落在 (48,41)）。
- 类型 3 的"非零字节即像素"与"`0x80` 后续字节是字面量份数"两种解法，在真实文件上可裁决：
  前者让 **48028/48028 行**正好产出帧宽个像素，后者只有 14732 行（337 个文件）。

**文件名规则**（art.ini，客户端 `ImageFinder` 一致）：

- `Theater=yes`：用剧场后缀 `.tem` / `.sno` / `.urb`，否则用 `.shp`。
- `NewTheater=yes`：图形名首字母落在 `GNCY`、次字母落在 `ATUDLN` 时，把**第 2 个字符**换成剧场字母
  （温带 `T`、雪地 `A`、城市 `U`），找不到再试通用字母 `g`，再退回原名。
- 实测命中：温带 `NAWALL` → `ntwall.shp`（`temperat.mix`），雪地 `NAWALL` → `nawall.shp`（`snow.mix`）；
  `SROCK01` → `srock01.tem`（`temperat.mix`）；`LOBRDG26` → `lobrdg26.tem`（`isotemp.mix`）。
- 图形档案按客户端给出的次序依次找：温带 `isotemp.mix` → `temperat.mix` → `tem.mix`，
  雪地 `isosnow.mix` → `snow.mix` → `sno.mix`，城市 `isourb.mix` → `urb.mix` → `urban.mix`。

## 数据格式：TMP 地块与 theater 资源（已用真实档案核实）

`RA2.MIX` 里 `isotemp.mix`（温带地块，1035 条）是等距地形图块库；`temperat.mix`/`snow.mix`/`urban.mix`
是各剧场的附加素材；tile 控制表在 `local.mix`，**地形调色板在 `cache.mix`**。

参照实现：原版客户端的 `TmpFile` / `drawTileBlock`（压缩包里的 `js/app.js`），
它同时给出了子块头布局、菱形像素排布与透明索引 —— 下面每一条都与它对得上。

| 层          | 布局                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| TMP 头      | `i32 cellsX, cellsY`（格数）+ `i32 cellWidth, cellHeight`（每格像素，60×30）+ `i32 offset[cellsX*cellsY]`（子块偏移，0 = 该格无图形） |
| TMP 子块    | 头 52 字节（字段见下）+ `u8 pixels[cellWidth*cellHeight/2]` + 可选 `zData[同长]` + 可选两份额外数据                                   |
| 像素        | 8 位调色板索引，`0` 表示透明；只存菱形部分，逐行排布                                                                                  |
| tile 控制表 | `local.mix` 里的 `temperat.ini` / `snow.ini` / `urban.ini`（当年 TS 的 "Isometric Tile Control File"）                                |
| 调色板      | `RA2.MIX` → `cache.mix` 里的 `isotem.pal` / `isosno.pal` / `isourb.pal`（6 位分量，需 ×4）                                            |
| 图形命名    | `<FileName><两位序号>[a..z]<剧场后缀>`，后缀 `.tem` / `.sno` / `.urb`（与客户端实现一致）                                             |
| 通行性      | `[General]` 锚点是**地块集编号**（`WaterSet=21` 即第 21 集 Water、`CliffSet=10`、`BridgeSet=19`、`BlackTile=6`）                      |

子块头 52 字节（相对子块起点）：

| 偏移 | 内容                                                                                 |
| ---- | ------------------------------------------------------------------------------------ |
| 0    | `i32 pixelX, pixelY`：该格在图块内的像素位置（等距斜向，可为负）                     |
| 8    | `u32 size`：像素 + z 数据的总字节数（含头；**不含**额外数据）                        |
| 12   | `u32 imageDataEnd`：像素区结束位置 = 52 + 像素数                                     |
| 16   | `i32 extraDataOffset`：第二份额外数据的块内偏移                                      |
| 20   | `i32 extraX, extraY, extraWidth, extraHeight`：额外数据的位置与格数                  |
| 36   | `u32 flags`：bit0 有额外数据、bit1 有 z 数据                                         |
| 40   | `u8 height, terrainType, rampType`；43 起 `i8` 雷达左右色各 3 字节；49 起 3 字节填充 |

菱形像素的逐行排布：上半 `cellHeight/2` 行，行宽 4、8、…、`cellWidth`，每行起点左移 2；
下半逐行宽 −4、起点右移 2。行宽之和恒等于 `cellWidth × cellHeight / 2`（60×30 → 900 字节）。
实现见 `tmpTileRows`（`packages/formats/src/tmp.ts`）。

判定依据：

- 1×1 地块（`Clear01.tem`）长度 1872 = 16 头 + 52 子块头 + 900 像素 + 900 z 数据；
  子块的 `size` 恒为 1852 = 52 + 900 + 900，`imageDataEnd` 恒为 952 = 52 + 900。
- 带额外数据的地块（flags bit0）步长 = 1852 + 780 × 2，且子块头 +16 处的
  `extraDataOffset` = 1852 + 780 —— 额外数据是同一份的两拷贝，`size` 不含它们。
- 三个剧场全部条目过一遍：**2218 个地块、10296 个子块**（空槽 995）全部解析通过；
  余下 1087 条不是地块（SHP 签名 `00 00 宽 高 帧数`），按格式拒绝。
- 子块的 `pixelX/pixelY` 每步是 (+30, +15) = 一格，正是等距斜向排布。
- 按"地块编号 → 图形文件"解析 Maps01.mix 首张地图用到的 130 种地块：**6720 个格子全部命中文件**
  （雪地地块表共 798 块，这张地图只用到 130 块，其余与它无关）。
- `isotem.pal` 的 119 号色是 (140,144,84)、121 号是 (132,144,68)，与温带草地一致；
  `isosno.pal` 的 21..29 号是雪白。温带地图渲染出来的直方图与原始截图同族（绿为主色）。

未核对：`height` / `terrainType` / `rampType` / 雷达色的语义；两份额外数据的内容与用途；
`flags` 的 bit2（实测在部分地块上为 1）。

### 实测补充（地图渲染暴露出来的）

- **透明索引是 `0`**：客户端只在索引非 0 时写入像素，菱形的四角都是 0。
- **`0xCD` 是 MSVC 的未初始化填充**：早期把子块头当 16 字节、像素当 `cellWidth*cellHeight`，
  于是把头部里 `0xCDCDCDCD` 的 `extraX/extraY/extraWidth/extraHeight` 当成了"菱形四角"，
  据此得出过"透明索引是 0xCD"的错误结论；按 52 字节头 + 半格像素修正后，四角自然是 0。
- **偏移 0 的子块槽位 = "这一格没有图形"**：多格悬崖图块（`Cliff*.sno`，2×3 / 3×2）常见，
  空缺由相邻格的重叠图形盖住；修正后 Maps01.mix 首张地图 6720/6720 格全部有图形。
- **高度填充块在 RA2 数据里不存在**：`snow.ini` 的 `HeightBase=46` 指向「ZMM Height Pieces」
  （`FileName=hyte`、15 块），但 `hyte*.sno` 在 `snow.mix`/`isosnow.mix`/`temperat.mix`/`isotemp.mix`/`local.mix`
  里都不存在 —— 这一组是后来版本（YR 一系）才有的，RA2 地图靠自身存的 Cliff 图块表现悬崖。
- **水域地块本身有完整图形**：`Water01..14` 的解出结果分别是 4 个 / 1 个子块，像素全部非透明
  （1×1 的 900/900）。上一条"水域是空洞、要靠引擎动画层填"的结论来自错误的 TMP 布局，
  已作废；整张地图（含水域）实测 6720/6720 格全部有图形。水面**动画**是另一回事，尚未实现。
- **立体感来自地图自带的悬崖图块，不需要按 `z` 抬高**：把一张带悬崖的温带地图（MULTI.MIX 第 7 张，
  52×53、218 格悬崖）按平铺渲染，崖脊、坡面、土路都完整 —— 说明 `z` 不是渲染用的垂直偏移，
  按它抬高反而会在地形没有悬崖图块处留下竖向空洞。红线：先抬高会在错的地方挖洞。
