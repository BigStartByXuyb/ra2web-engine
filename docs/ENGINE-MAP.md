### `FUN_005129c0` — 规则集加载（VA 0x5129c0–0x513070，1713 字节）

证据：`work/decompiled/ra2-engine/fn-512cac.md`（伪代码 + 引用 + 调用关系）。

行为：枚举 `RULE*.INI` → 逐个加载 → 再加载 `RULES.INI`、`ART.INI`、`LANGRULE.INI`、`AI.INI`；
失败时用 `DialogBoxParamA` 弹窗报错。

| 字符串                    | 地址     | 引用指令            |
| ------------------------- | -------- | ------------------- |
| `RULE*.INI`               | 0x7dbb6c | 0x5129e7            |
| `RULES.INI`               | 0x7dbb60 | 0x512a73 / 0x512b88 |
| `ART.INI`                 | 0x7dbb58 | 0x512c83            |
| `Failed to load ART.INI!` | 0x7dbb3c | 0x512cac            |
| `LANGRULE.INI`            | 0x7dbb2c | 0x512d8c            |
| `AI.INI`                  | 0x7dbb24 | 0x512f98            |

关键调用：`KERNEL32.FindFirstFileA / FindNextFileA / FindClose`、`USER32.DialogBoxParamA`、
内部 `FUN_0051ad50`（INI 对象构造，对象大小 0x50）、`FUN_004696b0`（容器构造）、
`FUN_00783290`（数组插入搬移）。调用方为 `FUN_005116a0`。

**对实现的意义**：这是全部单位数值的入口。`packages/rules` 的加载顺序必须与之一致
（先 `RULE*.INI`、后 `RULES.INI`、再 `ART.INI`/`LANGRULE.INI`/`AI.INI`），
这样 MOD 的覆盖语义才与原版相同。

## 数据格式：MIX 加密头布局（已用真实档案核实）

在真实 `RA2.MIX` 上验证通过的布局（`packages/formats/src/mix.ts` 实现，见 `mix-encrypted.test.ts`）：

| 偏移  | 内容                                                   |
| ----- | ------------------------------------------------------ |
| 0..3  | flags（`uint32`，含 `0x00020000` 表示加密）            |
| 4..83 | Blowfish 密钥材料（80 字节）                           |
| 84..  | 加密索引；其**前 8 字节同时充当"条目数 + 数据区长度"** |

要点：密钥材料的起点是 **4 而不是 0** —— 解析器在进入加密路径前已经读掉了 4 字节 flags。
条目表按 8 字节块解密，数据区起点 = 84 + 表长 + 对齐填充。

这一条曾让实现反复解出错误的条目数（25522 / 25863 而非 21）；错位 4 字节的表现是"解密成功但内容是垃圾"。

## 数据格式：地图 `[IsoMapPack5]`（已用真实档案核实）

在真实 `Maps01.mix` 上核实的布局（`packages/formats/src/map.ts` + `lzo1x.ts`，见 `map.test.ts`）：

| 层   | 布局                                                                                         |
| ---- | -------------------------------------------------------------------------------------------- |
| 文本 | 地图是 INI（windows-1252），`[Map] Size=` 给 left,top,right,bottom                           |
| 编码 | `[IsoMapPack5]` 是数值键的 base64 文本，按键的**数值升序**拼接                               |
| 容器 | 解码后是若干块：`u16 压缩长度` + `u16 原始长度` + LZO1X 压缩数据（单块原始数据 ≤ 8192 字节） |
| 记录 | 每 11 字节：`u16 rx`、`u16 ry`、`i16 tile`、`i16 保留`、`u8 subTile`、`u8 z`、`u8 保留`      |
| 坐标 | `cellX = rx − ry + width − 1`，`cellY = ⌊(rx + ry − width − 1) / 2⌋`                         |

判定依据全部来自数据本身：

- 首张地图（70×96、SNOW）解压前数据里 `11 00 00`（LZO 结束标记）恰好出现 **18 次**，
  而 `⌈11 × (2×70−1) × 96 / 8192⌉ = 18`；块头解出的"压缩长度 / 原始长度"与实际解码长度逐块一致。
- 18 块原始数据合计 146 788 字节 = `11 × (2×70−1) × 96 + 4`（多出的 4 字节是原版余量）。
- 记录数 = `(2×宽−1)×高` = 13 344，其中**正好 6 720 条（= 70×96）落在方格范围内且互不重复**，
  其余是同格的另一半菱形位置 —— 这条恒等式同时验证了坐标换算。
- 该地图实测：tile 索引 178 种（最多 713 / 734 / 0 / 326），z 只有 4 种取值（2 最多，其次 6）。

未核对：`z` 的原版单位（做高度渲染时需要）。

## 数据格式：TMP 地块与 theater 资源（已用真实档案核实）

`RA2.MIX` 里 `isotemp.mix`（温带地块，1035 条）是等距地形图块库；`temperat.mix`/`snow.mix`/`urban.mix`
是各剧场的附加素材；tile 控制表与调色板都在 `local.mix`。

| 层          | 布局                                                                                                             |
| ----------- | ---------------------------------------------------------------------------------------------------------------- |
| TMP 头      | `i32 x, y`（格数）+ `i32 cx, cy`（每格像素，60×30）+ `i32 offset[x*y]`（子块偏移）                               |
| TMP 子块    | `i32 pixelX, pixelY`（该格在图块内的像素位置，可为负）+ `u32 size` + `u32 待核对` + `u8 pixels[cx*cy]`           |
| 像素        | 8 位调色板索引，`0` 表示透明                                                                                     |
| tile 控制表 | `local.mix` 里的 `temperat.ini` / `snow.ini` / `urban.ini`（当年 TS 的 "Isometric Tile Control File"）           |
| 调色板      | `local.mix` 里 4 个 768 字节条目（6 位分量，需 ×4）                                                              |
| 图形命名    | `<FileName><两位序号>[a..z]<剧场后缀>`，后缀 `.tem` / `.sno` / `.urb`（与客户端实现一致）                        |
| 通行性      | `[General]` 锚点是**地块集编号**（`WaterSet=21` 即第 21 集 Water、`CliffSet=10`、`BridgeSet=19`、`BlackTile=6`） |

判定依据：

- 子块偏移严格等差（本样例 1852 字节 = 16 字节头 + 1800 像素 + 36 字节余量），
  且 `16 + 16 + 子块数 × 1852` 与文件长度逐项吻合（1×1 → 1872、2×4 → 14864、7×4 → 51984）。
- 把 7×4 地块的 28 个子块按各自 `pixelX/pixelY` 贴到同一张图上，拼出连贯的等距地块轮廓，
  透明区正好落在地块形状之外 —— 这条同时验证了像素起点、像素尺寸与"按头部偏移贴图"的做法。
- 子块的 `pixelX/pixelY` 每步是 (+30, +15) = 一格，正是等距斜向排布。
- 按"地块编号 → 图形文件"解析 Maps01.mix 首张地图用到的 130 种地块：**6720 个格子全部命中文件**
  （雪地地块表共 798 块，这张地图只用到 130 块，其余与它无关）。

未核对：子块头里的第 4 个 `u32`（实测恒为 952，与像素数/2 相关）；像素之后的 36 字节；
4 个调色板条目与 theater 的对应（按"最常出现的索引映射后应是棕/灰/土色"推断第一个
`hash=b10a9944` 是地形色板，其余三个分别是高亮、灰度、饱和色板）；tile 索引 → 地块文件的映射表。

### 实测补充（地图渲染暴露出来的）

- **透明索引是 `0xCD`**：地块图形的菱形四角都是这个值；把它当颜色画出来会让相邻格互相覆盖，
  整片地图糊成均匀条纹。`0` 是正常颜色（暗部），不能当透明。
- **偏移 0 的子块槽位 = "这一格没有图形"**：多格悬崖图块（`Cliff*.sno`，2×3 / 3×2）常见，
  空缺由相邻格的重叠图形盖住；修正后 Maps01.mix 首张地图 6720/6720 格全部有图形。
- **高度填充块在 RA2 数据里不存在**：`snow.ini` 的 `HeightBase=46` 指向「ZMM Height Pieces」
  （`FileName=hyte`、15 块），但 `hyte*.sno` 在 `snow.mix`/`isosnow.mix`/`temperat.mix`/`isotemp.mix`/`local.mix`
  里都不存在 —— 这一组是后来版本（YR 一系）才有的，RA2 地图靠自身存的 Cliff 图块表现悬崖。
- **水域是引擎自己画的动画层**：地图里约 545 个格子用 Water 集（如 326 → `Water*.sno`），
  渲染时这些区域的图形是空的（透明），由引擎的动画水面层填充；我们用静态地块渲染时它们就是空洞。
- **立体感来自地图自带的悬崖图块，不需要按 `z` 抬高**：把一张带悬崖的温带地图（MULTI.MIX 第 7 张，
  52×53、218 格悬崖）按平铺渲染，崖脊、坡面、土路都完整 —— 说明 `z` 不是渲染用的垂直偏移，
  按它抬高反而会在地形没有悬崖图块处留下竖向空洞。红线：先抬高会在错的地方挖洞。
